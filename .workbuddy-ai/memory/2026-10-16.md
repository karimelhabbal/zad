# 2026-10-16

## Mushaf reader: fill-width vertically scrollable mode — BUILT

**User's request** (after I refused the `cover`/stretch route, and after they
had rejected cropping on 2026-10-15): they chose the width-filled scrollable
option ("do first solution"). I recommended it and built it.

**What it does.** The page is drawn at the full screen **width** with its own
aspect ratio preserved, so it grows *taller* than the viewport, and the reader
scrolls vertically to reach the rest. The width is filled edge to edge, the
type is materially larger than the old fit-to-screen version, and **not one
line is hidden** — nothing is cropped and nothing is stretched.

**Implementation** — `lib/features/quran/mushaf_reader_screen.dart`, inside
`_MushafPageViewState.build`:
```dart
final pageHeight = constraints.maxWidth / MushafRepository.pageAspectRatio;
...
InteractiveViewer(
  panEnabled: false,          // horizontal drag must stay a page-turn
  minScale: 1, maxScale: 5,
  child: SingleChildScrollView(
    physics: pageHeight > constraints.maxHeight
        ? const ClampingScrollPhysics()
        : const NeverScrollableScrollPhysics(),
    child: SizedBox(
      width: constraints.maxWidth,
      height: pageHeight,
      child: image,
    ),
  ),
)
```
- `Image.file(fit: BoxFit.contain)` — deliberately **not** `BoxFit.fill`. The
  `SizedBox` is built from the same ratio as the bitmap so box and image ratios
  agree exactly and it resolves to a 1:1 fill. Using `contain` means that if the
  two ever drift apart the page letterboxes instead of stretching — distorted
  Arabic letterforms are worse than a thin margin.
- `NeverScrollableScrollPhysics` when the page would be *shorter* than the
  viewport: on a tablet (screen ratio ~0.625) the width-fitted page may fit
  vertically, and then there is nothing to scroll.
- Gesture layering is safe: `PageView` (horizontal) and the scroll view
  (vertical) resolve in Flutter's gesture arena per-axis, so swiping to change
  page and dragging to scroll coexist. Tap-thirds nav and pinch-zoom unchanged.

**New API** — `lib/data/repositories/mushaf_repository.dart`:
`static const double pageAspectRatio = 622 / 917;` (0.6783). Both sources serve
the same 622×917 sheet, so this belongs to the edition, not to one file.

**Layout arithmetic (verified, 622/917 = 0.6783):**
| screen | ratio | page height at full width | outcome |
|---|---|---|---|
| 1080×2340 (19.5:9) | 0.4615 | 1592px vs 2340 | overflows → scrolls, width exact |
| 720×1600 | 0.4500 | 1061px vs 1600 | overflows → scrolls, width exact |
| 800×1280 tablet | 0.6250 | 1179px vs 1280 | fits → no scroll, ~92% filled |

On a phone the page overflows by ~32%, so roughly a third of the page is
reached by scrolling. Expected and intended.

**Constraints honoured:** no `BoxFit.cover`, no `ClipRect`, no `Clip.hardEdge`,
no axis stretch anywhere. `python tool/check_dart_balance.py` passes on both
edited files. See `MEMORY.md` — cropping a Mushaf page is a hard rule.

**Not yet done (pending user feedback):** whether they like it, and the
unresolved `MushafRepository.fallbackUrl` licence risk recorded on 2026-10-15.

## SUPERSEDED — vector pages replaced the width-scroll approach

The section above is history. The same day, the user pushed back again — the
scrolling UX was "bad ux" — and sent a screenshot from the **simpro** app
(«القرآن الكريم مصحف التجويد») showing pages that fill the screen on the whole
mushaf. That screenshot was the key to the whole problem.

**What the screenshot actually proved.** Measuring it (640×1280) gave a page
ratio of ≈ **0.59–0.63**, not the 0.678 of the KSU scans. So simpro is *not*
showing photographs — it renders pages drawn to fit the screen. My earlier
claim that "fill and completeness are mutually exclusive" was only true of the
scan assets I had chosen, not of the problem.

**The real fix: vector pages.** `quran.ws` publishes the 604-page Madinah
mushaf as **SVG**, vectorised from the KFQC masters, with a per-ayah polygon
layer (`github.com/quran-ws/quran-svg`). Page `viewBox` is `345 550`
(ratio **0.6273**) — close to simpro's, and, crucially, *no fixed pixel size*.
A vector page is laid out to whatever box it is given, so "whole page" and
"fills the width" stop competing: `contain` fills the width edge to edge and
the page is never cropped or stretched.

**Verified licence (the earlier blocker, now cleared).** The KFQC usage-rights
statement quoted in the repo's `NOTICE.md` permits free use in "websites,
**software**, and other similar intermediates". The only restriction is the
physical **print-for-commercial-sale** trade, which is not what an app does.
The polygon/metadata layer is CC BY 4.0 with attribution waived inside a
product. So the clean route I said needed "written permission from KFQPC"
turned out to be published under the Complex's own standing permission.

**Implemented:**
- `pubspec.yaml` — added `flutter_svg: ^2.3.0` (resolved 2.3.0).
- `MushafRepository` — new edition `'madani_svg_kfqc'`; `pageAspectRatio =
  345/550`; `.svg` files; primary source
  `https://cdn.quran.ws/svg/pages/v1.1.1/hafs-kfqc/NNN.svg` (version-pinned,
  immutable), fallback the GitHub raw path. Minimum page size guard raised to
  20 KB (smallest real page is >100 KB). The old `madani_ksu` cache directory
  is simply not read, so existing users re-download once.
- `_MushafPageViewState.build` — `SvgPicture.file` with `BoxFit.contain`
  filling `constraints.maxWidth × maxHeight`, wrapped in `InteractiveViewer`
  (`panEnabled: false`, `minScale: 1`, `maxScale: 4`). The
  `SingleChildScrollView`/`SizedBox`/`pageHeight` machinery is gone.
- Background behind the page is the **paper colour** (`0xFFFFFFFF` light /
  `0x101314` dark) so the small vertical remainder reads as part of one sheet.
- l10n download prompt updated: ~80 MB over the network, ~340 MB on disk.

**Size trade-off (measured, worth knowing):** vector pages average ~570 KB,
totalling ~340 MB on disk versus ~82 MB for the old scans. On the wire the CDN
serves them **zstd-compressed** — a typical page is ~160 KB — so a full
download moves ~80 MB. Recorded as `MushafRepository.approximateFullSizeMb`.

**Verification:** `pub get` had to go through
`<flutter>/bin/cache/dart-sdk/bin/dart.exe pub get` (the `flutter` wrapper
crashes on process spawn here — see the 2026-10-15 tooling note).
`tool/check_dart_balance.py` passes on all four edited files;
`tool/analyze_via_lsp.py` reports **0 errors / 0 warnings / 0 infos over 69
files**. A page SVG was downloaded from both hosts, parsed as XML, and its
structure confirmed (26 `g`, 23 `path`, no `text`/`image`/`use`/`filter`/CSS —
the cleanest possible input for `flutter_svg`).

**Left open:** whether the user is satisfied; and the old unlicensed
`Kader4658/Quran_Pages` fallback URL — now **removed** from the repository, so
