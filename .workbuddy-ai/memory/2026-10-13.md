# 2026-10-13 — Zad: the recitation play button

## The complaint
"زر تشغيل صوت القارئ لا يعمل بعد تعديل الكود" — the play button in the recitation
bar does nothing. Session 4 had just rewritten the whole audio path.

## Root cause: the pre-flight probe was allowed to veto playback
Session 4 inserted a mandatory HTTP probe *before* every play:

```dart
final probe = await _probe(url);
if (probe != AudioProbe.ok) { await _fail(...); return; }   // ← never plays
```

Only `200/206` counted as `ok`. Everything else — a transport error, a 10 s
timeout, a captive portal, a carrier proxy, or the browser refusing a
cross-origin `Range` request — became a hard "do not play".

That last one is fatal and deterministic on **Flutter web**: `cdn.islamic.network`
sends **no `Access-Control-Allow-Origin`** header (verified with curl, with and
without an `Origin` header), so `package:http`'s XHR is blocked by CORS and the
probe returns `offline` — even though `audioplayers_web` plays the very same URL
through an `<audio>` element, which is exempt from CORS. The probe is a Dart-side
HTTP client; the audio is played by the platform stack (MediaPlayer / `<audio>` /
Media Foundation). They are not the same capability, and the probe was being
treated as if it were.

## The fix (`lib/state/audio_controller.dart`)
- **Only a definitive CDN answer may block playback**: `missing` (404) and
  `forbidden` (403) still fail fast with an accurate message. `ok`, `offline` and
  anything unexpected now fall through to the player, which is the authority.
- If the player then fails *and* the probe had seen the network as unreachable,
  the error is reported as `network` rather than blaming the recording.
- **Load tokens** (`_loadToken` / `_playerToken`): a load spans two awaits (probe,
  then prepare) and either can take seconds. `stop()` now bumps the token, so a
  load the user cancelled can no longer call `play()` when it finally returns and
  start a recitation on its own. A late cancelled load only tears the player down
  if it still owns it.
- `lib/features/quran/quran_audio.dart`: the loading spinner in `_TransportButton`
  is now an `IconButton` — tapping it cancels the prepare. Before, the user was
  locked behind a dead spinner for up to the platform's 30 s prepare timeout with
  no way out.
- New l10n key `audio.cancelPrepare` in both `strings_ar.dart` and
  `strings_en.dart` (key sets re-verified identical).

## Session 2 — the analyzer actually works, and it found a real bug

### Correcting the record above
The claim that `tool/analyze_via_lsp.py` "cannot work as written" was half wrong.
The legacy protocol was a red herring. The real blocker was **my reader**: the
server frames each message with **two** headers —
`Content-Length: N\r\nContent-Type: application/vscode-jsonrpc; charset=utf-8\r\n\r\n{json}` —
so consuming a single header line leaves the blank line in the stream and the
following `read(n)` swallows it, shifting every body by two bytes. Nothing parses,
`initialize` is never seen, and the run blocks until its deadline. The old script's
`unparsed` list is the smoking gun: `['Content-Length: 2777', '}}Content-Length: 75',
'Content-Type: application/vscode-jsonrpc; charset=utf-8', …]`.

Second trap: the AOT snapshot needs ~5–8 s to boot. An `initialize` sent the
instant it is spawned is silently dropped. Wait, and retry if unanswered.

`tool/analyze_via_lsp.py` is now a working LSP client (boot delay + retry,
header-draining reader, `$/analyzerStatus` used as the "analysis finished" signal,
idle fallback, exits 1 on errors). `dart format --output=none` is also useful on
this host: it runs the real parser in-process, so it validates **syntax** across the
whole tree even when `dart analyze` cannot start.

### The bug it caught — `test/audio_controller_test.dart` did not compile
Three `undefined_identifier` errors for `AppLifecycleState` (lines 662/675/676).
`package:flutter_test/flutter_test.dart` does not re-export it, so the whole test
suite would have failed to compile the moment `flutter test` could run again — the
`lifecycle` group was dead code, and nobody could have noticed on this host. Fixed
with `import 'package:flutter/widgets.dart' show AppLifecycleState;`.

Also fixed `tool/verify_offline.dart:139` (`unused_local_variable`: `for (final
(surah, verse) in sabr)` → `(_, verse)`), the only other diagnostic in the project.

### Also removed
`lib/state/audio_controller.dart` imported **both** `flutter/foundation.dart` and
`flutter/widgets.dart`, which is an `unnecessary_import`: `widgets.dart` reaches
`ChangeNotifier` through `src/widgets/basic.dart`, which re-exports it from
foundation. The foundation import is gone. (An earlier note called this a false
positive "because the analyzer wasn't resolving packages" — wrong: `.dart_tool/
package_config.json` exists and resolution is fine.)

## Session 3 — Mushaf source, dark mode, and Egypt's prayer calendar

Two user requests: a better source for the 604 Mushaf page images (they "aren't
good, especially in dark mode"), and prayer times matching what Egypt publishes.

### The Mushaf images were not the printed page at all
Downloaded and **looked at** the current primary (`Kader4658/Quran_Pages` via
jsDelivr, 1024×1656, 42 KB): it is a **text render**, not a scan. Aspect ratio
0.618 against the printed page's 0.678, and the text occupies the top ~45% of
the page with the rest blank. The README claimed "a real scan of the printed
604-page Madinah Mushaf" — that claim was false. Comparing against page 2 made
it obvious: the printed page is the fully illuminated gold-framed page.

New primary: **`https://quran.ksu.edu.sa/png_big/{page}.png`** — the Electronic
Mushaf project at King Saud University, which says on its own site
«القراءة من نسخة حقيقية مصوّرة من صفحات مصحف المدينة المنورة». 622×917 PNG,
~135 KB/page, ~82 MB for the set, 1..604 all present, HTTP 200 with any
User-Agent (including `Dart/3.13 (dart:io)`), works over plain HTTP too.
Verified visually: page 1 = Al-Fatihah illuminated, page 2 = Al-Baqarah 1-5.

- `MushafRepository.edition = 'madani_ksu'`; pages now live in
  `<appSupport>/mushaf/<edition>/`, so pages cached by earlier builds are never
  served again. `clearCache`/`cacheSizeBytes` cover every edition.
- Licensing is **improved but still not settled**: institutional host instead of
  anonymous mirrors, but no published terms of use were found. Needs written
  permission from KSU, or KFGQPC assets, before a store release.
- `tool/fetch_mushaf_assets.py` fetches all 604 for bundling (resumable,
  validates PNG/JPEG headers, prints the pubspec snippet). Bundling costs ~82 MB
  APK; on-demand download + cache remains the default.

### Dark mode
The page is white paper with black ink and was rendered with no filter at all.
Added `MushafPageTreatment { auto, asPrinted, dim, invert }` (persisted in
`AppSettings`), applied in `_MushafPageView` as a `ColorFiltered` **inside** the
gesture layer so taps/swipes/zoom are untouched.

`invert` is not a plain inversion: scale 0.92 + offset 234.6 maps white paper to
exactly 0 (true black on OLED) and black ink to 235 (soft off-white) instead of
glaring 255. Verified by rendering the real matrix over the real page with
Pillow — legible light-on-black text, gold ornament reads as muted teal.

### Prayer times — the default method was simply wrong for Egypt
Default was `ummAlQura` (Makkah). Egypt's calendar is the **Egyptian General
Authority of Survey**: Fajr 19.5°, Isha 17.5°.

`tool/verify_prayer_times.dart` pins the real `PrayerTimesService` against the
authority's published table for 2026-05-19 (EEST, UTC+3), eight cities from
Alexandria 31.2°N to Aswan 24.1°N, comparing **UTC instants** so the host
timezone is irrelevant. Before: Fajr/Sunrise/Asr/Maghrib/Isha 0-1 min,
**Dhuhr 1-2 min late** → 1 failure.

Cause found by measurement: `adhan`'s Egyptian preset carries
`methodAdjustments.dhuhr = +1`; the authority prints the plain transit. With it
cancelled (`params.adjustments = PrayerAdjustments(dhuhr: -methodAdjustments.dhuhr)`),
Dhuhr matches exactly in 7 of 8 cities, Cairo +1. **Now 48/48 within ±1 minute.**

Also: `AppSettings.calculationMethod` and `fromStorage` now default to
`egyptian`, and `SettingsRepository` gained a `revision` stamp (2) so existing
installs are migrated — a stored *legacy default* (`ummAlQura`) is corrected
once, while a deliberately chosen method is left alone.

### Gotcha for next time
`package:matcher` has **no `within` matcher** in this version — `within(minutes:
1, from: x)` fails with "`distance` is required". Use
`expect(delta.inMinutes.abs(), lessThanOrEqualTo(1))`. And project CLI tools
write through `stdout.writeln`, not `print`, because `avoid_print` is enabled.
